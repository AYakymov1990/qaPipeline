## Передумови

- Тестове замовлення на стенді (не прод); ID замовлення.
- Авторизація під акаунтом із потрібною роллю.

## Параметри (з коду `QAOrdersController.cs`, гілка `feat-seur-delivery`)

- Доступ — роль BPanel `FullAccess`, `QA` або `TestUsers`; для `emulate-auto-reject-order` і `shift-date` замовлення має бути тестового покупця або продавця, інакше 400 «Аккаунт не тестовый».
- `PATCH /api/v1/qa/orders/shift-date?orderId=<id>&shiftDay=<N>` — зсуває всі дати замовлення, коментарів і статусів; **від'ємне N — у минуле**, додатне — у майбутнє.
- `GET /api/v1/qa/orders/emulate-auto-reject-order?orderId=<id>` — автоскасування за поточним статусом: «WaitingSellerComfirmation» / «Paid» / «WaitingPayment» — лише якщо минув дедлайн статусу (інакше 200 «Не закончилось время жизни заказа…»); «WaitingDeparture» — скасовує одразу, без перевірки часу. Відповідь «Успех! Предоплата: <результат>».

## Кроки

1. Зсунути дати замовлення: `PATCH api/v1/qa/orders/set-creation-date`, `set-update-date` або `shift-date` (зсув усіх дат на N днів).
2. Емулювати джобу, якщо треба автоматичну дію: `POST api/v1/qa/orders-notification/{orderId}/complete` | `reject` | `notpaid-reject` | `notprocessed-reject`; або `GET api/v1/qa/orders/emulate-auto-reject-order` — автоскасування за поточним статусом.
3. Або виконати дію користувача, яка стала доступною після дедлайну (напр. відмова покупця від відправленого замовлення).

Інші корисні виклики `api/v1/qa/orders`: `set-ttn` (номер накладної), `refund-hold` (повернення холду без зміни статусу; платіж має бути в `hold_wait`), `confirm-hold`, `complete-order`, `close-order`. Статус тестової ТТН змінюється через `api/v1/qa/delivery-tracking-status`.

## Як перевірити результат

- Статус замовлення змінився (або дія зʼявилась у покупця / продавця).
- Для холдів — статус платежу в Профіті / Stripe.

## Особливості площадок

- Дедлайни округлюються під розклад джоб — див. CodeWiki § Заказы/Статусы-и-дедлайны.

## Відомі проблеми

- Тестові ТТН (напр. Genei `00000021`, `00000022`) не йдуть до реального перевізника й обходять перевірку «номер уже зайнятий» — їх статус змінюється тільки через QA API.
- Для Seur тестових ТТН немає: номери з SEUR PRE — справжні номери тестового середовища.
