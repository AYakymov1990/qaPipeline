# Аналіз змін у коді (етап 0c)

Мета — знати до тест-дизайну, що розробник **реально** змінив, а не лише що написано в задачі.

**Головне правило: код показує, ЩО перевіряти і ДЕ ризики. Очікуваний результат — тільки з вимог** (задача, відповіді, `qa-context/`). Якщо код розходиться з вимогою — це питання або дефект, а не нова вимога. Інакше помилка розробника стає «еталоном» тесту.

## Де код і що з ним можна

- Шлях до репозиторію AvtoPro — з `work/<ID>/00-input/test-data.md` (поле «Код AvtoPro»); немає — спитай QA і запиши туди.
- Гілка розробника — з того ж поля (туди її записує `qa-ado-fetch` з розділу Development задачі). Поточна гілка в AvtoPro інша — скажи QA, яку гілку переключити на Mac, і не аналізуй чужу.
- Код підключено **тільки для читання**. Ніколи не змінюй файли AvtoPro і не запускай команд, що пишуть у його `.git`: `checkout`, `merge`, `fetch`, `pull`, `commit`, `stash`, `clean`, `reset`. Гілку готує QA на Mac до запуску.
- Дозволено: `git diff`, `git log`, `git show`, `git grep`, `git blame`, читання файлів. Додавай `--no-optional-locks` до git-команд, щоб git не намагався писати.
- Помилка `dubious ownership` — один раз виконай `git config --global --add safe.directory <шлях>` (це конфіг пісочниці, не репозиторію).

## Порядок

1. **База і гілка.** Поточна гілка — `git -C <шлях> rev-parse --abbrev-ref HEAD`; база — `origin/master`, якщо є, інакше `master`. Зафіксуй у шапці: гілка, коміт HEAD, база, коміт `merge-base`.
2. **Огляд.** `git diff --stat <база>...HEAD` і `git log --oneline <база>..HEAD`. Три крапки в diff — тільки зміни гілки, без того, що прийшло з master.
3. **Групи файлів**: бекенд (контролери / API, сервіси, репозиторії), фронт (сторінки, компоненти), ресурси й переклади, міграції БД, конфіги й прапорці, фонові задачі (JobRunner), тести, інфраструктура. Згенеровані, lock- і бінарні файли — пропусти, лише згадай.
4. **Факти для тестування** з кожної значущої зміни (з посиланням `шлях:рядок`):
    - **ендпоінти**: метод, маршрут, нові чи змінені поля, валідації, коди помилок, права доступу;
    - **валідації й ліміти**: числа, формати, обовʼязковість — з констант, атрибутів, умов;
    - **тексти UI і переклади**: нові чи змінені ключі і значення по локалях; ключ, якого немає для частини локалей, — ризик;
    - **площадки**: перевірки ID площадки, `GetSite`, доменів — де діє зміна;
    - **ролі й користувачі**: ролі, знижки, рівні лояльності, тестові користувачі (`StaticUserHelper.TestUsers`);
    - **feature flags**: назва, де перевіряється, поведінка увімкнено / вимкнено;
    - **статуси й переходи**: `OrderStatusEnum` та інші, TTL, автопереходи, скасування;
    - **фонові задачі**: що роблять, інтервал;
    - **інтеграції**: зовнішні API, тестовий / бойовий контур, обробка помилок і таймаутів;
    - **міграції**: таблиці, поля, значення за замовчуванням, зміна наявних даних;
    - **помилки й логи**, які буде видно в Console / Network.
5. **Вплив.** Хто викликає змінені методи й компоненти (`git grep` за назвою) — модулі для регресу. Покриття цих місць автотестами — наступний крок, скіл `qa-autotests-coverage` (проєкт AvtoProAutomation).
6. **Звірка із задачею** (`00-input/requirement.md`, коментарі, `01-review.md` / `02-spec.md`, якщо є):
    - **Неописані зміни** — є в коді, немає в задачі;
    - **Не знайдено в коді** — є в задачі, не знайдено в цій гілці (може бути в іншій гілці чи сервісі — не стверджуй, що не зроблено);
    - **Розбіжності** — зроблено інакше, ніж описано: цитата вимоги + що в коді, `шлях:рядок`.
7. **Документація.** Якщо CodeWiki підключено — для ключових змін звір, чи описано цю поведінку в документації (`qa-docs-lookup`). Змінено те, що описано в CodeWiki, — розділ «Документація ↔ код»: «документацію треба оновити: <що>». Це сигнал для команди, не дефект.
8. **Запиши** `work/<ID>/00-input/code-changes.md` за `templates/code-changes.md`.
9. **Підсумок у чаті** — 3–6 рядків: що змінено, на яких площадках, ризики, скільки розбіжностей. Розбіжності — запропонуй або передати в `qa-req-review` (питання / RD), або одразу коментарем розробнику чи аналітику.
10. **Маршрут.** Якщо зміни зачіпають ознаки L (гроші, статуси, інтеграції, міграції, кілька модулів), а маршрут S чи M — запропонуй підняти маршрут.
11. **Контекст.** Факти загального значення (статуси, TTL, ліміти, назви прапорців, ключі перекладів, де що лежить у коді) — у блок «Зберегти в контекст?» з джерелом `[код: шлях, коміт]` (скіл `qa-context-update`).
12. **Журнал** — рядок у `work/<ID>/pipeline.md`.

## Правила

- Не оцінюй якість коду і не роби code review — тільки те, що потрібно для тестування.
- Фрагменти коду в артефактах — не довше 5 рядків і тільки коли без них незрозуміло; інакше `шлях:рядок`.
- **Секрети** з конфігів (ключі, рядки підключення, паролі, токени) — ніколи не переносити в qaPipeline, навіть частково.
- Великий diff (сотні файлів) — спершу огляд за групами, потім деталі тільки там, що стосується задачі; скажи QA, що пропущено.
