# Критерії ревʼю вимог

Проходь блоки, що стосуються вимоги. Блок, який не стосується, пропускай мовчки.

## A. Повнота

- **Ролі**: анонім; покупці без знижки / 2% / 3% / 5% / 10%; продавці без знижки / 10% / 20%; автосервіс 20%; адміністратор. Що бачить і що може кожна роль? Чи відрізняються ціни, доступні дії, тексти?
- **Локалі**: es (основний фокус), ua, pl, pt, ru-версія, tr (у розробці). Тексти й переклади, валюта, формати дат, телефонів, адрес, часові пояси, доступні способи оплати і доставки.
- **Стани сутності**: усі статуси і переходи; що видно і що доступно в кожному статусі; хто може змінити статус.
- **Негативні сценарії**: помилки валідації, недоступність сервісу, відсутність прав, конкурентні дії (два користувачі одночасно).
- **Порожні та проміжні стани**: немає даних, завантаження, таймаут, частковий успіх.
- **Платформи**: десктоп, мобільний веб / адаптив (межі ширини), мобільний застосунок.
- **Нотифікації**: email / push / SMS — тригер, отримувач, мова, текст.
- **Дані**: обовʼязковість полів, формати, ліміти, граничні значення, значення за замовчуванням.

## B. Однозначність

Слова-маркери, що вимагають уточнення:

- «швидко», «зручно», «коректно», «правильно», «як зазвичай», «як зараз» (без посилання на поточну поведінку);
- «відповідне повідомлення», «помилка» — без точного тексту чи ключа перекладу;
- «за потреби», «за можливості», «тощо», «і т. д.», «та інше»;
- «за замовчуванням» без значення; кількісні слова без чисел («кілька», «багато», «великий файл»);
- займенники, для яких неочевидно, до чого вони відносяться.

## C. Узгодженість

- З бізнес-правилами `BR-…` у `qa-context/domain/`.
- З іншими твердженнями цієї ж вимоги.
- З термінами `qa-context/glossary.md` (одна назва — одне поняття).
- Між текстом і макетами.
- З поточною поведінкою продукту, якщо вимога її змінює.

## D. Тестованість

- Є вимірюваний очікуваний результат.
- Відомі точні тексти кнопок, повідомлень, ключі перекладів.
- Зрозуміло, як перевірити: UI, API (Swagger), DevTools (Network / Console), база, адмінка.

## E. Права і конфігурація

- Feature flags: поведінка при увімкненому / вимкненому, хто перемикає.
- Права доступу: хто може, хто не може, що бачить той, хто не може.
- Видимість даних між ролями: приватні та публічні дані, чужі обʼєкти.

## F. Інтеграції

- Stripe: успіх, відмова, 3-D Secure, скасування, повернення коштів.
- Доставка в Іспанії: Genei і кастомні варіанти продавців.
- Зовнішні API: поведінка при помилці, таймауті, неочікуваній відповіді.

## G. Вплив і регрес

- Які суміжні модулі зачіпає зміна.
- Існуючі дані: старі замовлення, міграція, кешовані значення.
- Зворотна сумісність: стара версія мобільного застосунку, старі посилання, збережені фільтри.

## H. Нефункціональні (якщо релевантно)

- Продуктивність: обсяги даних, час відповіді.
- Безпека: доступ до чужих даних, валідація на бекенді, а не лише в UI.
- Доступність: клавіатура, підписи полів, контраст.
- Аналітика: які події трекаються.

## Типи дефектів вимог (RD)

| Тип | Коли |
| --- | --- |
| Неповнота | Бракує сценарію, ролі, стану, локалі, обробки помилки |
| Неоднозначність | Можна зрозуміти двома способами |
| Суперечність | Конфлікт усередині вимоги, з BR, з макетом, з іншою вимогою |
| Нетестованість | Немає вимірюваного очікуваного результату |
| Термінологія | Одне поняття названо по-різному або різні — однаково |
| Ризик | Технічно складно, зачіпає критичний шлях, загрожує регресом |
