# Баг-репорт (етап 5)

Мета — однаковий, відтворюваний баг-репорт, який QA переносить у Azure DevOps без правок. Баг у Azure DevOps заводить **QA сам**; скіл тільки готує текст.

## Вхід

- **Від QA**: опис у чаті, скріншот, відео, задача — будь-що з цього.
- **Від агента**: FAIL зі звіту `05-runs/<дата>/report.md`, кейс `TC-xxx.md`, скріншоти. FLAKY і «потребує рішення QA» — **не** оформлюй без підтвердження QA.
- Контекст: `work/<ID>/00-input/test-data.md` (стенд, площадка), `02-spec.md` / `03-checklist.md` (очікуваний результат), `qa-context/PROJECT.md` § 10 (severity, priority).

Якщо бракує кроків або незрозуміло, що мало статися, — спитай QA тільки про це, коротко. Решту заповни з контексту.

## Що написати

За `templates/BUG.md`, файл `work/<ID>/bugs/BUG-xxx.md` (наступний вільний номер). Баг без задачі — `work/_bugs/YYYY-MM-DD-<коротко-латиницею>.md`.

1. **Заголовок** — `[<версія площадки>][<роль>] <Модуль>: <що відбувається> <за якої умови>`. Коротко, без «не працює» без деталі. Приклад: `[ES][Покупець 5 %] Кошик: знижка не перераховується після зміни кількості`.
2. **Передумови** — стенд і площадка (хост і домен), тип тестового користувача (без логінів і паролів), стан даних, увімкнені прапорці, потрібні cookie.
3. **Кроки відтворення** — нумеровані, мінімальні, з чистого стану, з конкретними даними (артикул, сума, email); тексти UI — дослівно в лапках. Перший крок — відкрити конкретну сторінку.
4. **Фактичний результат** — що відбувається: дослівні тексти, числа з валютою, статус; помилка в Network / Console — метод, ендпоінт, код. Без здогадок про причину.
5. **Очікуваний результат** — конкретно і з посиланням на джерело: REQ / AC, CHK, «Опис задачі» або домовленість (коментар, грумінг).
6. **Докази** — файли, які QA прикріпить до бага.
7. **Severity і priority** — запропонуй за визначеннями `PROJECT.md` § 10 у шапці файлу; остаточно вирішує QA.

## Видача

- У чаті — **готовий блок для Azure DevOps**: заголовок окремим рядком, нижче — передумови, кроки, фактичний і очікуваний результат у вигляді, придатному для вставки в поле «Repro Steps». Плюс запропоновані severity / priority і список файлів для вкладення.
- Статус файлу — «чернетка». QA підтвердив — «підтверджено QA». QA завів і назвав номер — впиши `ado_id`, статус «заведено».

## Правила

- Один баг — одна проблема. Дві різні поведінки — два баги.
- Кроки мають відтворюватися з чистого стану людиною, яка не бачила задачі.
- Без емоційних слів і оцінок («жахливо», «зовсім не працює»).
- Без паролів, токенів і персональних даних реальних користувачів.
- Мова — українська; тексти UI — дослівно.

## Самоперевірка

- Заголовок за формулою, з площадкою і роллю.
- Передумови містять стенд і тип користувача.
- Кроки нумеровані і конкретні; фактичний відрізняється від очікуваного; очікуваний має джерело.
