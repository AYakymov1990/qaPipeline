# Тест-чек-лист (етап 3)

Застосовується щоразу, коли треба написати чек-лист для нового функціоналу, доопрацювання або регресу окремого блоку.

**Перед написанням прочитай `references/quality-rules.md`** — правила атомарності, тест-дизайну і контролю обсягу обовʼязкові для кожної перевірки.

## Вхід — від найповнішого до найпростішого

1. **`work/<ID>/02-spec.md` погоджено QA** (маршрут L) — перевірки будуються від REQ / AC; колонка «Вимога» — `REQ-001 / AC-001.1`.
2. **Тільки `01-review.md`** (маршрут M) — перевірки від тверджень `S`, відповідей із `01-answers.md` і припущень; «Вимога» — `S-03`.
3. **Тільки опис задачі** (маршрут S) — спершу міні-ревʼю (нижче), потім перевірки; «Вимога» — «Опис» або номер пункту опису.

Якщо `02-spec.md` є, але зі статусом «чернетка» — попроси QA погодити його або підтвердити, що писати від чернетки.

**Міні-ревʼю для маршруту S** (без окремого файлу): пройди опис за блоками A, B, D з `qa-req-review/references/review-criteria.md`. Неясне спершу пошукай у CodeWiki (`qa-docs-lookup`), якщо вона підключена. Неясності — коротким списком у полі «Питання» опису чек-листа, кожна з прийнятим припущенням. Якщо знайшов ознаку маршруту L (гроші, статуси, інтеграції — див. `qa-pipeline`) — скажи QA і запропонуй підняти маршрут.

## Контекст

Якщо є `work/<ID>/00-input/code-changes.md` — використай його, щоб перевірки влучали в реальні зміни: точні межі й ліміти, ключі перекладів і локалі без перекладу, площадки й прапорці з коду, ендпоінти для перевірок у Network. «Вплив і регрес» — для регресійних рядків («автотести» або «вручну»); «Неописані зміни» — окремий блок перевірок з позначкою в «Вимога»: «код, не описано». Очікуваний результат — із вимог, не з коду.

Прочитай `qa-context/PROJECT.md` (площадки й функції «тільки тут», ролі, валюти, тестові користувачі, зони ризику) і `glossary.md` (терміни). Із `domain/` — сутності, яких стосується задача. Контекст продукту бери звідти, а не з памʼяті.

## Формат видачі

Джерело правди — **`work/<ID>/03-checklist.md`** за `templates/03-checklist.md`. Excel для команди генерується з нього:

```bash
python3 .claude/skills/qa-checklist/scripts/build_xlsx.py work/<ID>/03-checklist.md
```

Скрипт створює `03-checklist.xlsx` поруч і виводить попередження (нумерація, пріоритети, мітки регресії) — виправ їх у md і запусти ще раз. Правки після видачі — теж у md, потім перегенерація.

Якщо QA явно просить інший формат (документ, повідомлення, таблицю в іншому інструменті) — віддай у ньому, зберігши структуру і зміст.

### Excel (що робить скрипт — не змінюй без потреби)

- Один аркуш, що прокручується цілком: спершу опис, потім таблиця. **Без закріплених областей** (`freeze_panes = None`), без макету «фіксована шапка + прокрутка».
- Рівно **6 колонок**: № / Перевірка / Очікуваний результат / Пріоритет / Вимога / Результат.
- «Пріоритет» — умовне форматування кольором; «Результат» — порожня, випадаючий список Pass / Fail / Blocked / Skip з кольорами.
- Розділи (ролі, фінальні блоки) — темні обʼєднані рядки; блоки — світлі обʼєднані рядки; вони не нумеруються.

### Колонки md

| Колонка | Що писати |
| --- | --- |
| № | Наскрізна нумерація на весь чек-лист, включно з регресією. Номер = ID перевірки: № 7 → `CHK-007` у кейсах і багах |
| Розділ | Роль («РОЛЬ 1. Покупець — гість») або фінальний блок: «Наскрізні сценарії», «Локалізація», «Регресійні перевірки» |
| Блок | Сценарій усередині розділу з нумерацією: «1.1 Доступ», «1.2 Оформлення» |
| Перевірка | Що перевіряємо, з конкретними тестовими даними; регресія — з префіксом «[Регресія]» |
| Очікуваний результат | Конкретно, з точними текстами повідомлень і кнопок, числами з валютою |
| Пріоритет | Критичний / Високий / Середній / Низький |
| Вимога | REQ / AC, `S-xx` або «Опис» — залежно від входу |
| Виконання | агент / вручну / API / автотести — за `qa-agent-cases/references/agent-suitability.md`; у xlsx не потрапляє |
| Результат | Необовʼязкова. Заповнює `qa-agent-run` для рядків «агент» (Pass / Fail / Blocked) або QA; переноситься в xlsx |

## Мова і зміст перевірок

- Проста, зрозуміла мова без зайвого жаргону — чек-лист має бути зрозумілим будь-кому в команді, не лише QA.
- Українською, навіть якщо задача російською. Назви кнопок і тексти UI — в лапках, як в UI / ключах перекладів.
- Конкретні тестові дані одразу в тексті перевірки (email, суми з валютою, знижки, телефони, VIN, держномери, артикули) — спершу з `qa-context/test-data.md` (спільний довідник), потім з `work/<ID>/00-input/test-data.md`; як отримати потрібний стан — з `qa-context/howto/`. Не «ввести валідні дані».
- Перевірка і дія — в одному рядку, без «Крок 1 / Крок 2», якщо не попросили.

## Структура

Якщо у функціоналі беруть участь різні ролі — таблиця будується за ролями:

1. **Розділ ролі** — «РОЛЬ 1. Покупець — гість», «РОЛЬ 2. Продавець VIPro».
2. **Блоки сценаріїв** усередині ролі — «1.1 Доступ», «1.2 Створення замовлення».
3. Після ролей — **«Наскрізні сценарії»** (повний шлях між ролями чи системами: покупець оформлює → продавець обробляє → покупець бачить результат), потім **«Локалізація»**, потім **«Регресійні перевірки»**.

### Регресія — в тому ж чек-листі

- Спершу перевірки на зміну, потім розділ «Регресійні перевірки».
- Кожна регресійна перевірка починається з «[Регресія]».
- Нумерація наскрізна, без окремого лічильника.

### Групування без обʼєднання

Кілька перевірок зі спільним кроком (те саме поле, кнопка, сценарій), але різними даними чи аспектами результату — **окремі рядки поспіль** в одному блоці, не один рядок і не розкидані по документу.

Приклад:
1. Поле «Email»: порожнє → помилка «Поле обовʼязкове».
2. Поле «Email»: «test@», «test.com» → помилка «Невірний формат email».
3. Поле «Email»: «test@example.com» → значення прийнято, перехід далі.

Це не суперечить правилу «без дублювання»: тут різна поведінка. Однакова поведінка для кількох ролей чи площадок — одна перевірка з переліком.

## Що обовʼязково покрити

- Кожен AC (маршрут L) або кожне твердження `S` (маршрут M) — хоча б однією перевіркою; непокрите — в «Покриття вимог» з причиною.
- Стани сутності, яких стосується задача: що видно і що доступно в кожному; дозволені і значущі заборонені переходи.
- Граничні значення лімітів — тільки там, де поведінка на межі різна.
- Права доступу і feature flags: увімкнено / вимкнено / адмін.
- Видимість даних між ролями (приватне / публічне, чуже).
- Перевірки через API (Swagger) і DevTools (Network / Console), де поведінку не видно в UI.

## Особливості AvtoPro

- **Площадки**: функція може працювати лише на частині площадок (`PROJECT.md` § 2). Перевір площадки, де працює, і хоча б одну, де не повинна. Валюта в очікуваному результаті — за площадкою.
- **Ролі і знижки**: покупці (гість / зареєстрований / верифікований; 0 / 2 / 3 / 5 / 10 %), продавці (без знижки, «міні-PRO» −10 %, VIPro і VIPro+ −20 %), СТО, консьєрж. Окремі рядки — тільки для ролей і знижок з різною поведінкою; для решти — одна перевірка з переліком (таблиця рішень).
- **Оплата і Recalvi**: тільки під тестовим користувачем — вкажи це в перевірці. Stripe — тестові картки.
- **Фонові задачі**: якщо результат зʼявляється після JobRunner, `sendorder` (5 хв), трекінгу (10 хв) чи TTL — вкажи в очікуваному результаті, коли перевіряти.
- **Видача**: тестові продавці видно тільки з cookie `showTestUsers`.
- **Платформи**: десктоп і мобільна версія сайту; мобільні застосунки — поза скоупом.
- Тестування — на тестовому стенді після збірки; стенд — в описі чек-листа.

## Розподіл: агент / вручну / автотести

Для кожного рядка заповни «Виконання» за `qa-agent-cases/references/agent-suitability.md`:

- агент перевіряє **новий функціонал задачі** — там, де він швидший за людину (багато даних, повтор під ролями чи площадками, ланцюжок кроків, Network / Console);
- регресійні перевірки, які покривають наявні автотести, — «автотести»;
- решта — «вручну».

Наприкінці — блок «Зберегти в контекст?» з фактами і тестовими даними, корисними для інших задач (формат і правила — скіл `qa-context-update`). Немає таких — блок не показуй. Типові кандидати: нові артикули, тестові продавці; тексти UI з макетів і перекладів, яких немає в глосарії; нові терміни задачі.

У підсумку в чаті вкажи розподіл: скільки рядків агенту, вручну, автотестам — і сумнівні рядки, якщо є.

## Самоперевірка перед видачею

- Кожна перевірка атомарна, ствердна, без «перевірити коректність» — і відповідає `references/quality-rules.md`.
- Немає дублів для ролей, площадок і даних з однаковою поведінкою; техніки тест-дизайну застосовано там, де вони скорочують перевірки без втрати покриття.
- Обсяг визначено складністю і ризиками, а не цільовою кількістю.
- Опис містить функціонал, зміну, задачу, маршрут, скоуп (з регресом), стенд, джерела, підказку для «Результату».
- Розділи: ролі → наскрізні → локалізація → регресія; регресія з міткою «[Регресія]»; нумерація наскрізна.
- У кожного рядка: перевірка з тестовими даними, конкретний очікуваний результат, пріоритет, вимога.
- «Покриття вимог» заповнено (маршрути L і M).
- Скрипт відпрацював без попереджень; xlsx без закріплених областей.
- Мова проста, без русизмів.
