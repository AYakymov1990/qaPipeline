# Правила якості чек-листа

Обовʼязкові для кожної перевірки. Перечитуй перед написанням і перед видачею.

## Атомарність

Кожна перевірка перевіряє **рівно одну умову**.

| Погано | Добре |
| --- | --- |
| Перевірити створення замовлення, застосування знижки і надсилання листа | Замовлення створюється при валідних даних |
| | Знижка застосовується, якщо виконано умову X |
| | Після створення замовлення надсилається лист Y |

Формулювання:

- короткі;
- однозначні;
- ствердні;
- без зайвих вступних слів;
- зрозумілі без читання вихідного коду.

Не використовуй розмиті формулювання:

- «Перевірити коректність…»
- «Перевірити, що все працює…»
- «Переконатися в правильній поведінці…»

Замість цього описуй конкретний очікуваний результат.

## Без дублювання

Не дублюй однакові перевірки:

- під різні ринки (площадки);
- під різні ролі;
- під різні дані —

якщо реальної різниці в поведінці немає. Однакова поведінка для кількох ролей чи площадок — одна перевірка з переліком їх у формулюванні.

## Тест-дизайн

Застосовуй техніки там, де вони **зменшують кількість перевірок без втрати покриття**.

### Класи еквівалентності

Не створюй десятки однакових перевірок для значень, що обробляються однаково. Один представник класу — одна перевірка.

### Граничні значення

Якщо є ліміти, діапазони, дати, кількість, ціни — розглядай:

- безпосередньо нижче межі;
- межу;
- безпосередньо вище межі —

але тільки якщо ці значення справді мають різну поведінку.

### Таблиці рішень

Для комбінацій:

- ролей;
- знижок;
- умов;
- feature flags;
- прав доступу;
- інших бізнес-умов.

Не розмножуй усі математично можливі комбінації, якщо частина з них еквівалентна.

### Переходи станів

Для:

- статусів замовлення;
- статусів сутностей;
- workflow;
- станів погодження;
- переходів між станами.

Перевіряй дозволені і значущі заборонені переходи.

### Error guessing

Додавай сценарії, що випливають з реалістичних ризиків реалізації:

- null / порожнє значення;
- відсутні дані;
- неправильний стан;
- повторна дія;
- race / retry — якщо такий ризик випливає з реалізації;
- неконсистентні дані;
- помилки інтеграції.

Не створюй штучних edge cases, не повʼязаних зі зміною.

## Контроль обсягу

Кількість перевірок визначається виключно:

- складністю задачі;
- кількістю змінених сценаріїв;
- ризиками;
- кількістю значущих бізнес-умов.

Не встановлюй штучного мінімуму чи максимуму перевірок. Не роздувай чек-лист заради кількості. Не урізай чек-лист заради стислості, якщо це призводить до втрати значущого покриття.
