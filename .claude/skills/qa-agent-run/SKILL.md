# Прогін агентом (етап 4b)

Агент виконує кейси нового функціоналу в браузері через Playwright MCP на локальному компʼютері QA (IP з доступом до стендів) і повертає QA результат з доказами.

## Перед стартом — обовʼязкові перевірки

Будь-яка не пройдена — **зупинись** і скажи QA, що не так.

1. Є `work/<ID>/04-cases/_index.md` і кейси зі статусом «готовий» або «стабільний». Кейси «чернетка» — тільки якщо QA прямо дозволив.
2. Є `work/<ID>/00-input/test-data.md` зі стендом і регіональною версією.
3. **Захист від проду.** Хост кожного `env` з `.env` відповідає шаблону `^(avto|es|pt|pl|tr|ua)\.seller[1-5]\.vus\.us$`. Інший хост (зокрема avto.pro, avtopro.*) — не відкривай.
4. Акаунти кейсів є в `.env`. Значення паролів використовуй тільки для входу — **ніколи** не записуй їх у звіти, кейси, чат чи коміти.
5. Playwright MCP доступний (інструменти браузера є в сесії). Немає — попроси QA перевірити `.mcp.json` і перезапустити Claude Code.

## Прогін

1. Створи `work/<ID>/05-runs/YYYY-MM-DD-HHMM/`.
2. **Доступ до стенду**: якщо відкрилась сторінка пароля закритої площадки — введи `TEST_ENV_PASSWORD`; cookie `TestEnvAccessToken` діє 7 днів.
3. Для кожного кейсу, у порядку `_index.md`:
    - почни з чистого стану: потрібний акаунт (перевір імʼя користувача в шапці сайту), потрібний хост, cookie `showTestUsers`, якщо кейс вимагає;
    - `platform: mobile-web` — розмір вікна 390×844;
    - виконуй кроки за знімком доступності сторінки; перед кожною дією перевіряй, що хост — стенд;
    - для кожного пункту очікуваного результату зафіксуй **факт**: що саме показано (дослівна цитата, число), URL, запит у Network (метод, статус, ключове поле), помилки Console;
    - таблиця даних — пройди кожен варіант окремо, результат по кожному;
    - «Коли перевіряти» з очікуванням — чекай і перевіряй повторно не довше 15 хв;
    - скріншот — на кожному FAIL і BLOCKED, і на ключовому кроці кейсу; зберігай у `TC-xxx/`;
    - виконай «Очищення».
4. **Результат пункту:**
    - **PASS** — факт збігається з очікуванням дослівно (тексти) або точно (числа);
    - **FAIL** — не збігається. Повтори кейс один раз з чистого стану: знову FAIL → FAIL; тепер PASS → **FLAKY**;
    - **BLOCKED** — крок неможливо виконати (елемента немає, немає даних, помилка оточення) або очікування понад 15 хв;
    - факт неоднозначний (схоже, але не дослівно; невідомо, чи це очікувано) — **FAIL з позначкою «потребує рішення QA»**, а не PASS.
5. **Зупинка всього прогону**: капча, 429 / 423, перенаправлення на хост поза стендом, ознаки бойового контуру (сторінка реального банку, лист реальному клієнту) — зупинись, збережи доказ, повідом QA.

## Після прогону

1. **Звіт** — `05-runs/<дата>/report.md` за `templates/run-report.md`: підсумок, таблиця по кейсах, таблиця по CHK, деталі FAIL / BLOCKED / FLAKY.
2. **Результати в чек-лист** — у `03-checklist.md`, колонка «Результат» для рядків «агент»: Pass / Fail / Blocked (FLAKY → Blocked з приміткою у звіті). Ручні рядки не чіпай. Перегенеруй xlsx: `python3 .claude/skills/qa-checklist/scripts/build_xlsx.py work/<ID>/03-checklist.md`.
3. **Статуси кейсів** — оновлюй у `_index.md`: 3 прогони поспіль з однаковим результатом → «стабільний».
4. **Баги** — для кожного FAIL без позначки «потребує рішення QA» підготуй чернетку за правилами скіла `qa-bug-report` (`work/<ID>/bugs/BUG-xxx.md`, статус «чернетка»). Баги в Azure DevOps заводить QA сам.
5. **Контекст.** Дані, які на стенді спрацювали (товар є, продавець активний, прапорець увімкнено), — у блок «Зберегти в контекст?» з датою перевірки; дані з `qa-context/test-data.md`, які не спрацювали, — запропонуй позначити неактуальними (скіл `qa-context-update`).
6. **Підсумок у чаті** — 3–6 рядків: PASS / FAIL / BLOCKED / FLAKY, що потребує рішення QA, які чернетки багів готові, що лишилось вручну.

## Правила

- Не змінюй кейс під час прогону і не трактуй розбіжність на користь системи.
- Не вигадуй обхідних шляхів: якщо кнопки немає — це результат, а не задача.
- Не виходь за межі кейсу: побачив іншу проблему — запиши в звіт у розділ «Помічено поза кейсами», не досліджуй.
