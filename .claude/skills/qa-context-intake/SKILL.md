# Режим наповнення контексту

Окремий режим: тут ми **не працюємо над задачею**, а збираємо знання, які потім використовують усі скіли pipeline. Режим триває, доки QA не скаже «готово» / «вийти з режиму».

## Старт

Скажи QA одним-двома реченнями, що режим увімкнено і що можна надсилати будь-що: текст, списки, нотатки, скріншоти, транскрипції, файли. Нічого не записується без підтвердження.

## Для кожного повідомлення QA

1. **Розбери** вхід на окремі знання і визнач тип кожного:

    | Тип | Приклад | Куди |
    | --- | --- | --- |
    | Інструкція (як зробити) | «Щоб отримати замовлення в статусі X — …», «Як увімкнути прапорець Y» | `qa-context/howto/<тема>.md` + рядок в `howto/README.md` |
    | Тестові дані | артикули, продавці, VIN, картки, стан прапорців | `qa-context/test-data.md` |
    | Термін, синонім, назва в UI | «на pt це називається «…»» | `qa-context/glossary.md` |
    | Бізнес-правило, статуси, ліміти | «скасування після X → утримуються накладні витрати» | `qa-context/domain/<сутність>.md` |
    | Факт про площадки, ролі, оточення, процес, ризики | «на seller3 завжди свіжа збірка develop» | `qa-context/PROJECT.md` |
    | Де шукати в документації | «правила кешбеку — у зоні …» | `qa-context/sources.md` |

2. **Звір** з наявним контекстом: дубль — скажи, що вже є; суперечність — покажи «було / стало» і спитай.
3. **Уточни коротко** лише те, без чого знання не можна використати: стенд і дата для тестових даних; площадки і роль для інструкції; передумови. Не більше 3 питань за раз; чого QA не знає — так і запиши.
4. **Покажи прев'ю**: що і куди буде записано (для інструкції — повний текст рецепта). Формат блоку — як у `qa-context-update`.
5. **Запиши** після «так» (або «так 1, 3») за правилами запису зі скіла `qa-context-update`; скажи одним рядком, що куди додано.

## Інструкції (рецепти)

Кожна інструкція — окремий файл `qa-context/howto/<коротко-латиницею>.md` за `templates/howto.md`:

- одна мета — одна інструкція; кроки нумеровані, конкретні, тексти UI дослівно;
- обовʼязково: коли знадобиться, передумови (роль, стенд, доступи — назви змінних з `.env`), як перевірити результат, особливості площадок, «перевірено: стенд, дата»;
- поле **«Агенту можна виконувати»** — так / ні. «так» — тільки якщо всі кроки на сайті стенду під тестовим користувачем і без незворотних дій зі спільними даними; адмінка, БД, зовнішні системи — «ні», якщо QA прямо не сказав інакше;
- рядок у `qa-context/howto/README.md` (тема, файл, коли використовувати, агенту можна, перевірено).

Інструкція, що спирається на тестові дані (конкретний продавець, артикул), — посилається на `test-data.md`, а не дублює дані.

## Вихід із режиму

На «готово»: підсумок — скільки записів і куди, що лишилось непідтвердженим (збережи в `qa-context/_intake-pending.md`, щоб не загубилось), і пропозиція закомітити: `git add qa-context && git commit -m "Контекст: <що додано>"`.

## Правила

- Паролі, токени, ключі, персональні дані реальних людей — ніколи; паролі — тільки `.env`, в контексті — назва змінної. Якщо QA надіслав пароль — не записуй, нагадай про `.env`.
- Записуй слова QA як факт з джерелом `[зі слів QA, YYYY-MM-DD]`; не додавай від себе того, чого QA не казав.
- Мова — українська; терміни — з глосарію.
