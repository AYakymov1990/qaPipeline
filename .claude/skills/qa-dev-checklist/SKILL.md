# Чек-лист для розробника (етап 3b)

Мета — щоб задача приходила в тест уже робочою: розробник сам перевіряє основний функціонал і найчастіші причини повернення задачі. Це **не** скорочена копія QA-чек-листа і не перенесення тестування на розробника — лише мінімум, без якого тестувати немає сенсу.

## Вхід — від найповнішого

1. `work/<ID>/03-checklist.md` — основне джерело: відбір рядків за правилами нижче.
2. `02-spec.md` або `01-review.md` — якщо чек-листа ще немає (розробник отримує dev-чек-лист раніше, ніж готовий QA-чек-лист).
3. Опис задачі — для маршруту S.

Плюс `qa-context/PROJECT.md` (площадки, тестові користувачі, фонові задачі).

## Що включати

- **Основний сценарій** кожної REQ (або кожного ключового `S`) — happy path, одна перевірка на REQ.
- **Ключові негативні** — ті, що найчастіше ламаються при передачі: обовʼязкові поля, базова валідація, немає прав / не та роль.
- **Площадки**: по одній перевірці на кожну площадку, де поведінка відрізняється; і одна площадка, де функції бути не повинно (якщо застосовно).
- **Ролі і знижки** — тільки ті, від яких залежить основний сценарій; одна перевірка з переліком, якщо поведінка однакова.
- **Інтеграції й дані**: запит до API повертає очікуваний статус і поля; оплата / Recalvi — під тестовим користувачем; фонова задача (JobRunner, `sendorder`, трекінг) відпрацьовує.
- **Технічна готовність**: немає помилок у Console і 5xx у Network на сторінках задачі; міграції застосовані; feature flag увімкнено на стенді; тексти UI є для всіх площадок задачі (немає ключів перекладу замість тексту).

## Що не включати

- Повні класи еквівалентності і всі граничні значення — один представник.
- Регрес (покривають автотести).
- Візуальні дрібниці, тексти другорядних повідомлень, рідкісні edge cases з низьким пріоритетом.

Обсяг — за правилами `qa-checklist/references/quality-rules.md`: визначається задачею, без штучних мінімумів і максимумів. Кожен пункт атомарний, ствердний, з конкретним очікуваним результатом.

## Формат

Запиши `work/<ID>/03-dev-checklist.md` за `templates/03-dev-checklist.md`:

- пункти `DEV-01, DEV-02…` з посиланням на `CHK` (або REQ / `S`), щоб QA бачив звʼязок;
- мова — технічно зрозуміла розробнику: можна називати ендпоінти, поля, прапорці, таблиці, якщо вони відомі з джерел;
- тестові дані — конкретні (з `00-input/test-data.md`, якщо є);
- наприкінці — розділ «Що перевірятиме QA» (2–4 рядки про скоуп тесту) і «Готовність до тесту».

У тому ж файлі — **блок для коментаря в задачу Azure DevOps**, готовий до вставки: ті самі пункти чекбоксами `- [ ]` і прохання відмітити виконані перед переведенням у тест.

## Після видачі

- У чаті — 2–3 рядки: скільки пунктів, що свідомо не включено.
- Якщо QA потім знаходить баг, який покривав пункт dev-чек-листа, — у баг-репорті позначається `dev_check: DEV-xx` (це сигнал, що самоперевірку не пройшли або пункт сформульовано нечітко).

## Самоперевірка

- Кожна REQ (ключове `S`) має хоча б один пункт основного сценарію.
- Немає регресійних, візуальних і низькопріоритетних пунктів.
- Кожен пункт виконується розробником на стенді або локально без знання QA-документації.
- Блок для Azure DevOps збігається з основним списком.
