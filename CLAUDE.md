# Інструкції для Claude у цьому репозиторії

Це QA-репозиторій проєкту AvtoPro. Тут не пишемо продакшн-код — тут готуємо і виконуємо тестування.

## Завжди

- Перед будь-якою QA-задачею прочитай `qa-context/PROJECT.md` і `qa-context/glossary.md`. Деталі — з `qa-context/domain/` за потреби.
- Артефакти задачі — тільки в `work/<ID задачі>/`. ID = номер задачі в Azure DevOps (наприклад `work/12345/`); немає номера — коротка назва латиницею (`work/cart-discount/`).
- Мова артефактів — українська. Назви кнопок і тексти інтерфейсу — дослівно, в лапках, як в UI.
- Наскрізні ID: дефекти вимог `RD-001`, питання `Q-001`, вимоги `REQ-001`, перевірки `CHK-001`, кейси `TC-001`, баги `BUG-001`. Нумерація — в межах задачі.
- Факти — тільки з документації, `qa-context/` або відповідей QA. Решта — з позначкою `[ПРИПУЩЕННЯ]`.

## Ніколи

- Не записуй паролі, токени, ключі та персональні дані в будь-які файли, крім `.env`.
- Не відкривай продакшн-URL через Playwright MCP і не вводь реальні платіжні дані.
- Не створюй баги в Azure DevOps без явного підтвердження QA.

## Етапи pipeline

1. `qa-req-review` → `01-review.md`, `01-answers.md`
2. `qa-spec` → `02-spec.md` (заплановано)
3. `qa-checklist` → `03-checklist.xlsx` + `03-checklist.md` (заплановано)
4. `qa-agent-cases` / `qa-agent-run` → `04-cases/`, `05-runs/` (заплановано)
5. `qa-bug-report` → `bugs/` (заплановано)

Якщо в `qa-context/` бракує факту, потрібного кільком задачам, — запропонуй QA додати його туди (не додавай сам без згоди).
